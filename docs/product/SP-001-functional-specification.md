Chapter 1: Introduction to the WE Platform

1.1 Purpose of this Document

This document provides the official functional specification of the WE
Platform.

Where the Business Package (BP-001) explains why the WE Platform exists,
this specification explains what the platform is and how it functions.

It serves as the primary reference for everyone responsible for
designing, developing, implementing and maintaining the platform.

This document is intended to bridge the gap between educational
philosophy and software engineering.

Every function described within this specification should remain
consistent with the educational principles established in the WE
Platform Executive Summary.

1.2 Purpose of the WE Platform

The WE Platform is an integrated educational ecosystem designed to
improve learning by connecting every major educational process within a
single intelligent platform.

Instead of treating curriculum, teaching, assessment, reporting and
educational analysis as separate systems, the platform combines them
into one continuous learning environment.

The platform exists to help schools answer one important question:

How can we better understand every student's learning so that we can
help them succeed?

Everything within the platform has been designed to support this
objective.

1.3 Scope of the Platform

The WE Platform supports the complete educational lifecycle.

Its scope includes:

curriculum management;

Student Learning Profiles;

The platform is not designed to replace education.

It is designed to strengthen education.

1.4 Vision of the Platform

The long-term vision of the WE Platform is to become a complete
educational operating system for schools.

Every educational activity should be connected.

Every educational decision should be supported by meaningful evidence.

Every learner should receive personalised educational support.

Every teacher should have better educational information.

Every school should continuously improve through Educational
Intelligence.

1.5 Core Educational Principle

The WE Platform is built upon one central principle.

Learning is the centre of the entire system.

Everything else exists to support learning.

Curriculum supports learning.

Teaching supports learning.

Assessment supports learning.

Artificial Intelligence supports learning.

Technology supports learning.

If a feature does not improve learning directly or indirectly, it should
not become part of the platform.

1.6 Platform Philosophy

The WE Platform has been developed around several educational

Teachers Remain Central

It never replaces educational judgement.

1.7 What Makes WE Different

Many educational platforms manage educational information.

The WE Platform manages educational understanding.

Traditional systems answer questions such as:

What mark did the student receive?

Which class is the student in?

Intelligence.

Chapter 2: Overall Platform Architecture

2.1 Introduction

The WE Platform has been designed as an integrated educational ecosystem
rather than a collection of independent software applications.

Many educational systems currently used by schools have evolved over
time by adding separate modules for attendance, assessment, reporting,
communication and learning management. Although each system performs
valuable functions, they often operate independently, requiring teachers
and administrators to enter the same information multiple times.

The WE Platform takes a fundamentally different approach.

Instead of connecting separate software products, the platform has been
designed around a single educational architecture in which all
components contribute to one shared purpose:

Understanding and improving student learning.

Every module within the platform shares information through one common
educational framework.

This architecture reduces duplication, improves consistency and enables
Educational Intelligence to develop continuously.

2.2 Architectural Philosophy

The architecture of the WE Platform is based upon five principles.

Principle 1 --- One Student, One Learning Record

Every student has one central Student Learning Profile.

All educational information contributes to this profile.

Information is never duplicated unnecessarily.

Every module reads from and contributes to the same educational record.

Principle 2 --- One Educational Workflow

Every educational activity belongs to one continuous workflow.

Curriculum

↓

Planning

↓

Teaching

↓

Assessment

↓

Educational Evidence

↓

Student Learning Profile

↓

Educational Intelligence

↓

Teacher Decision

↓

Learning Support

↓

Continuous Improvement

No module operates independently.

Principle 3 --- One Source of Truth

Every important educational item should exist only once within the
platform.

Examples include:

student identity;

curriculum objectives;

learning objectives;

assessments;

teacher information;

classes;

parent information.

Other modules reference these records instead of creating copies.

This ensures consistency throughout the platform.

Principle 4 --- Modular Design

Each module has a clearly defined responsibility.

Modules communicate through secure services without becoming dependent
upon internal implementation details.

This enables:

easier maintenance;

future expansion;

independent upgrades;

improved reliability.

Principle 5 --- Education Drives Architecture

The architecture follows educational workflows rather than technical
convenience.

Every architectural decision should answer one question:

Does this improve learning?

If not, the architecture should be reconsidered.

3.1 Introduction

The educational workflow is the foundation of the WE Platform.

Unlike traditional educational systems that treat curriculum, teaching,
assessment and reporting as separate activities, the WE Platform
connects every educational process into one continuous workflow.

Every educational action contributes to future educational
understanding.

Every interaction strengthens the Student Learning Profile.

Every piece of educational evidence supports better educational
decisions.

This continuous workflow transforms the platform from a collection of
software modules into a living educational ecosystem.

The workflow described in this chapter forms the foundation for every
module described later in this specification.

No module should be developed independently from this educational
workflow.

3.2 Educational Workflow Philosophy

The workflow is based upon one simple educational principle:

Every educational activity should improve the understanding of student
learning.

This means that every classroom activity, assessment, observation or
intervention should contribute to the continuous development of the
student's educational profile.

The platform therefore views education as a continuous cycle rather than
a sequence of isolated events.

Learning is never considered "finished."

Instead, every activity creates new educational evidence that improves
future teaching and learning.

Chapter 4

User Roles and Permission Model

4.1 Introduction

The WE Platform serves a diverse educational community.

Each user interacts with the platform for different purposes and
therefore requires different levels of access.

A student needs to view personal learning progress.

A teacher needs to manage learning and assessment.

Parents need to understand their child's educational journey.

School leaders require whole-school Educational Intelligence.

System administrators maintain the technical platform.

Education authorities require approved educational information for
planning and policy.

For this reason, the WE Platform has been designed around a
comprehensive Role-Based Access Control (RBAC) model.

Every user receives only the permissions necessary to perform their
educational responsibilities.

This approach improves:

security;

privacy;

usability;

governance;

system reliability.

Most importantly, it protects student information while supporting
effective educational practice.

4.2 Permission Philosophy

The permission model follows several core principles.

Educational Purpose

Access should always support learning.

Users receive information because it assists their educational
responsibilities.

Least Privilege

Users receive the minimum permissions necessary.

Additional permissions require explicit authorisation.

Need to Know

Access is determined by educational need rather than organisational
status.

Being a senior staff member does not automatically provide unrestricted
access.

Transparency

Users should understand:

what they can access;

why they can access it;

who is responsible for granting access.

Accountability

Every significant action performed within the platform should be
traceable to an authenticated user.

4.5 Student Role

The Student role is designed to support learning while protecting
privacy.

Students may:

view personal dashboard;

view learning objectives;

view assignments;

complete assessments;

submit homework;

receive teacher feedback;

monitor personal progress;

view personal learning goals;

access approved learning resources;

communicate with teachers where permitted.

Students may not:

view other students' information;

modify assessment results;

change curriculum information;

access teacher notes;

view confidential observations;

approve AI recommendations;

access leadership dashboards.

Students always have access only to information relating to themselves.

4.6 Teacher Role

Teachers are the primary educational users of the platform.

Teachers may:

manage classes;

create learning activities;

record assessments;

record observations;

view Student Learning Profiles;

review Educational Intelligence;

assign interventions;

communicate with parents;

generate reports;

approve AI-generated suggestions;

manage classroom resources.

Teachers may not:

modify school-wide configuration;

access students outside authorised classes;

modify security settings;

access confidential leadership information.

Teachers retain professional responsibility for educational decisions.

4.7 Head of Department Role

Department leaders receive additional permissions.

They may:

monitor departmental curriculum;

review departmental assessment trends;

analyse Educational Intelligence;

support teacher planning;

review intervention programmes;

access departmental reports;

coordinate curriculum implementation.

Department leaders do not automatically gain unrestricted access to
unrelated departments.

4.8 School Leadership Role

School leaders require broader educational visibility.

They may:

view school dashboards;

monitor learning growth;

review intervention effectiveness;

analyse Educational Intelligence;

review curriculum implementation;

generate strategic reports;

monitor platform adoption;

communicate with staff.

Leadership permissions remain subject to school policy.

Confidential teacher notes remain protected unless explicitly
authorised.

4.9 Parent Role

Parents are educational partners.

Their permissions focus on supporting their own child.

Parents may:

view student progress;

view attendance;

receive reports;

receive school communication;

monitor learning goals;

view teacher-approved feedback;

communicate with teachers.

Parents may not:

view information relating to other students;

modify educational records;

access teacher-only notes;

approve assessments;

modify learning objectives.

Parent permissions are always linked to authorised student
relationships.

4.10 School Administrator Role

School administrators manage organisational configuration.

They may:

manage enrolments;

manage classes;

manage staff accounts;

manage parent relationships;

configure school settings;

assign permissions;

manage academic years;

generate administrative reports.

School administrators do not automatically access confidential
educational observations unless authorised.

4.11 System Administrator Role

System Administrators manage the technical platform.

Responsibilities include:

monitoring;

performance;

integration management.

System Administrators should not routinely access confidential
educational content.

Administrative authority does not imply unrestricted educational access.

4.12 Education Authority Role

Education Authorities may receive authorised access according to
applicable legislation and school agreements.

Examples include:

aggregated educational statistics;

curriculum implementation reports;

system-wide Educational Intelligence;

research datasets;

policy dashboards.

Individual student information should remain protected unless legally
authorised.

4.13 Research Role

Approved educational researchers may receive carefully controlled
access.

Research permissions must follow:

ethical approval;

privacy legislation;

school approval;

data governance policies.

Research access should normally use anonymised or aggregated
information.

4.14 AI Service Role

Artificial Intelligence operates as a controlled system service.

AI may:

analyse educational evidence;

prepare recommendations;

summarise reports;

identify patterns.

AI may not:

modify educational records independently;

approve interventions;

communicate directly with parents without review;

replace teacher judgement.

Every AI action must remain traceable.

4.23 Chapter Summary

The User Roles and Permission Model ensures that every user receives
access appropriate to their educational responsibilities while
protecting student privacy, supporting professional practice and
maintaining system security.

The WE Platform uses a flexible Role-Based Access Control model built
upon educational purpose rather than organisational hierarchy.

Permissions are carefully defined, fully auditable and designed to
evolve as the platform grows.

By combining security, transparency and educational responsibility, the
permission model forms one of the most important foundations of the WE
Platform.

Permission Principles

Every permission must have an educational purpose.

Users receive the minimum access necessary.

Students access only their own learning information.

Parents access only approved information relating to their own children.

Teachers remain responsible for educational decisions.

Artificial Intelligence never receives decision-making authority.

All significant actions are recorded through audit logs.

Privacy, accountability and security are integrated into every
permission decision.

The permission model is scalable and designed for future educational
roles.

Chapter 5: Student Learning Profile (Core Module)

5.1 Introduction

The Student Learning Profile (SLP) is the heart of the WE Platform.

Every module within the platform either contributes information to the
Student Learning Profile or uses information from it.

Unlike traditional Student Information Systems that primarily store
administrative records, the Student Learning Profile is designed to
become a continuously evolving representation of each student's
educational journey.

It is not simply a record of grades.

It is a living educational model that helps teachers, students, parents
and school leaders understand how learning is developing over time.

For software engineers, the Student Learning Profile should be
considered the central domain object of the entire WE Platform.

Every future module---including Assessment, Educational Intelligence, AI
Assistant, Reporting and Learning Gap Analysis---depends upon this
module.

5.2 Purpose of the Student Learning Profile

The Student Learning Profile exists to answer one educational question:

"What do we currently know about this student's learning, and what
should happen next?"

To answer this question, the profile combines educational information
from multiple sources into one integrated educational record.

The profile supports:

personalised learning;

educational decision-making;

continuous assessment;

intervention planning;

curriculum tracking;

educational reporting;

communication;

long-term learning growth.

The Student Learning Profile is therefore the foundation of personalised
education within the WE Platform.

5.3 Design Philosophy

The Student Learning Profile has been designed according to six
educational principles.

One Student

Each student has only one profile throughout their educational journey.

One Source of Truth

Educational information is stored once and referenced by all modules.

Continuous Growth

The profile develops continuously rather than only after examinations.

Evidence-Based

Every educational conclusion must be supported by educational evidence.

Teacher-Centred

Teachers remain responsible for interpreting and acting upon the
information.

Future-Oriented

The profile focuses not only on past achievement but also on future
learning.

5.23 Chapter Summary

The Student Learning Profile is the most important module within the WE

It provides a single, continuously evolving educational record for every
student by integrating curriculum progress, assessments, educational
evidence, learning behaviours, growth, teacher observations and

Rather than acting as a simple database of grades, the Student Learning
Profile becomes the educational memory of the platform.

Every major module contributes to it, and every important educational
decision is informed by it.

It is the foundation upon which personalised learning, Educational
Intelligence and continuous school improvement are built.

Core Principles

One student has one lifelong Student Learning Profile within the school.

Every educational event contributes to the profile.

Educational conclusions must always be evidence-based.

Teachers remain responsible for educational interpretation and
decisions.

Artificial Intelligence provides insights but never replaces
professional judgement.

The profile supports personalised learning and continuous growth.

The module serves as the central educational record for the entire
platform.

Every future educational module must integrate with the Student Learning
Profile.

Chapter 6

Curriculum Management Module

6.1 Introduction

The Curriculum Management Module is the educational foundation of the WE
Platform.

Every learning activity within the platform begins with the curriculum.

Without a clearly structured curriculum, it is impossible to:

define learning objectives;

measure student progress;

identify learning gaps;

provide personalised learning;

evaluate educational outcomes.

For this reason, the Curriculum Management Module is the first
operational module of the platform.

Every other educational module---including Assessment, Student Learning
Profile, Educational Intelligence and Artificial Intelligence---depends
upon the curriculum structure defined here.

The curriculum is not simply stored within the platform.

It drives the entire educational workflow.

6.2 Purpose of the Module

The Curriculum Management Module exists to organise, manage and maintain
the educational framework used by schools.

It enables schools to:

build curriculum structures;

organise subjects;

define learning objectives;

create micro-skills;

map assessments;

monitor curriculum coverage;

align teaching with curriculum requirements.

The module ensures that every educational activity can be traced back to
the curriculum.

6.3 Educational Philosophy

The WE Platform considers the curriculum to be more than a syllabus.

It represents the educational roadmap that guides teaching and learning.

The curriculum answers three fundamental questions:

What should students learn?

When should they learn it?

How will we know they have learned it?

The Curriculum Management Module provides the structure required to
answer these questions consistently across the platform.

10.1 Introduction

The Learning Gap Engine is one of the most powerful educational modules
within the WE Platform.

Traditional educational systems often identify students who are

prioritise intervention;

"What learning should this student already have mastered, but has not
yet demonstrated?"

10.3 Educational Philosophy

The Learning Gap Engine is based upon one important educational belief:

Every learning gap represents an opportunity for learning, not a label
for the learner.

Learning gaps should never define students.

Instead, they identify where educational support should be provided.

The purpose of identifying a learning gap is to improve learning---not
to categorise students.

The platform therefore presents learning gaps as educational
opportunities that can be addressed through appropriate teaching and
intervention.

10.7 Types of Learning Gaps

The WE Platform recognises several types of learning gaps.

Knowledge Gap

The student has not yet acquired essential knowledge.

Conceptual Gap

The student knows facts but does not understand underlying concepts.

Procedural Gap

The student understands the concept but cannot apply it correctly.

Application Gap

The student can complete routine tasks but struggles to apply knowledge
in unfamiliar situations.

Skill Gap

A practical or measurable skill has not yet reached expected mastery.

Prerequisite Gap

A missing earlier skill prevents successful learning of a more advanced
concept.

Retention Gap

Previously mastered learning has declined over time.

The platform records the type of learning gap where appropriate.
